\begin{abstract}
\noindent
Modern data pipelines increasingly cross boundaries that data engines have traditionally
implemented with separate execution paths: single-node and distributed execution, batch and
streaming, relational operators and model inference, and CPU and GPU work. \sys{} explores
how much of this fragmentation can be removed by imposing one restriction on the engine itself:
a stateful operator is admitted only if it can be expressed as a mergeable
\pcf{} triple over Apache Arrow. Under this contract, changing the partition count changes
scheduling rather than operator semantics, and the same state transition can be used for
incremental execution. Decode, embedding, and inference are represented in the same logical
plan rather than delegated to an opaque per-row path.

We evaluate the design first as a correctness invariant and then as a performance claim. All
22 TPC-H queries produce equivalent results through the single-node and distributed
executors, and the recovered results remain equivalent across five injected worker-loss
configurations. To separate execution from storage effects, DuckDB is measured both on its
native compressed representation and on the same Arrow input consumed by \sys{}. On identical
Arrow input, \sys{} is faster on every suite for which that controlled comparison is available,
by $2.8$--$26\times$; with DuckDB's native store, the comparison reverses on TPC-H at sf10.
These results suggest that storage representation and storage statistics account for a
substantial part of the remaining single-node gap, rather than execution kernels alone.

The evaluation also exposes costs that headline latency does not capture. On TPC-H sf1,
\sys{} uses $1.86\times$ the CPU while achieving $0.78\times$ the wall time, using
$2.4\times$ as many effective cores. In the measured fault-injection environment, shuffle
replication makes recovery more expensive than recomputation. Conversely, the shared
operators drain a streaming backlog at $3.2\times$ Spark Structured Streaming, and repeated
execution converges toward steady-state performance by the third run in a control experiment
that separates most cache-warming effects. \sys{} remains $1.29\times$ behind DuckDB on the
Join Order Benchmark, and its streaming and storage subsystems provide weaker guarantees than
mature specialized systems. Taken together, the results support mergeability as a practical
unifying constraint while identifying the cases where that constraint is insufficient or
costly.
\end{abstract}

\section{Introduction}
\label{sec:intro}
% ===========================================================================

Data systems have historically specialized along several boundaries: local versus distributed
execution, bounded versus unbounded input, relational versus model-centric processing, and CPU
versus accelerator work. Those boundaries were useful because each side imposed different
constraints. They are less useful when a single production pipeline routinely crosses several
of them. The result is often not one engine with several scheduling modes, but multiple
execution models connected by serialization, materialization, and application-level glue.

Two changes make that fragmentation increasingly visible. First, a single server can now
execute workloads that previously required a cluster, so paying distributed-runtime overhead
for every query is no longer an acceptable default. At the same time, continuously arriving
data has made incremental execution a normal requirement rather than a separate niche. Second,
modern pipelines contain operators whose costs and selectivities are difficult to know from a
catalog: regular expressions, Python callbacks, media decode, embedding models, and LLM calls.
They also mix devices, for example CPU decode followed by GPU inference and a CPU join. A plan
that cannot represent these operations cannot optimize across them.

\sys{} asks whether these boundaries can be reduced by constraining the operator vocabulary
rather than by adding another execution layer. A stateful operator is admitted only if it can
be expressed once as a mergeable \pcf{} triple over Arrow. The algebra is established; the
design choice is to make mergeability an admission criterion rather than an optional fast path.
That restriction gives the engine one semantic implementation of an operator while allowing
one core, many cores, and many nodes to differ in scheduling. The same representation also
provides an incremental state transition for micro-batch streaming.

The restriction does not cover all computation. Exact order statistics, global ordering, some
join forms, and stronger streaming state models require weaker contracts or remain outside the
distributed path (\cref{sec:price,sec:limitations}). This scope is important: the paper does
not claim that all data processing is mergeable. It asks whether a deliberately restricted
stateful core is broad enough to cover a useful set of relational, streaming, multimodal, and
inference workloads without maintaining separate operator implementations.
\cref{tab:vocab} states that boundary in full: what is admitted as a mergeable triple, what is
admitted under a weaker range-partitionable contract, and what is refused outright.

A second design choice follows from the first. Because the same operator semantics are used
across execution modes, observations such as cardinalities and strategy outcomes can be
associated with a stable operator identity and reused by later planning decisions. \sys{}
therefore combines static rules with measurements collected during and across executions.
Media decode, embedding, and inference are also represented as plan expressions, allowing the
same optimizer and resource manager to reason about them together with filters, joins, and
aggregations.

\subsection{Contributions}

This paper makes five contributions:
\begin{enumerate}\itemsep1pt \parskip0pt \topsep2pt
\item \textbf{A mergeability-first operator contract.} \sys{} makes the
\pcf{} factorization an admission criterion for stateful operators. The resulting algebraic
contract is property-tested over arbitrary partitionings, and operators that do not satisfy it
are explicitly identified rather than routed through a second general implementation
(\cref{sec:algebra,sec:price}).

\item \textbf{One operator implementation across execution scales and micro-batch streaming.}
Single-core, multicore, and distributed execution differ in how partial states are scheduled
and combined. The same state transitions are reused incrementally for streaming, with the
streaming-specific driver and checkpoint costs measured separately
(\cref{sec:streaming,sec:eval-streaming}).

\item \textbf{Measurement-driven planning with result-invariant adaptation.} \sys{} adapts
predicate order, aggregation strategy, memory sizing, and other result-equivalent physical
choices using observations collected at operator, stage, and cross-execution timescales. A
controlled repeated-execution experiment distinguishes this loop from ordinary cache warming
(\cref{sec:learning,sec:eval-learning}).

\item \textbf{Relational and model operators in one plan.} Media transforms, embeddings, and
inference are first-class expressions under the same logical plan, optimizer, memory manager,
and heterogeneous CPU/GPU scheduler as relational operators
(\cref{sec:interface,sec:pipeline}).

\item \textbf{An evaluation that separates latency, compute cost, storage effects, and failure
behavior.} The study reports correctness equivalence across schedulers, standard relational
benchmarks, controlled Arrow-versus-native-storage comparisons, CPU cost, streaming overhead,
GPU pipelines, and injected worker failures. It also reports negative results, including the
Join Order Benchmark gap, higher CPU consumption, and recovery behavior that does not justify
replication in the measured environment (\cref{sec:eval,sec:limitations}).
\end{enumerate}

\paragraph{Reading the numbers.}
\label{sec:convention}
Unless otherwise stated, a ratio written \bx{} is
$\text{\sys{}}_{ms}/x_{ms}$ for baseline $x$, so \textbf{values below 1.00 indicate lower
\sys{} latency}. Suite-level ratios are geometric means over the included queries. Bar charts
invert this ratio and report speedup, where larger is better. DuckDB appears in two distinct
configurations: \emph{native store}, after an untimed ingest into DuckDB's compressed,
dictionary-encoded, zone-mapped representation; and \emph{same Arrow}, where DuckDB executes
the same zero-copy Arrow input given to \sys{}. The native-store result reflects the system as
normally used, while the same-Arrow result is intended to isolate execution more directly from
physical storage representation.

\section{Mergeable operators across execution scales}
\label{sec:algebra}
% ===========================================================================

A common source of divergence is that the same logical operator is implemented through
different physical paths at different scales. A \texttt{GROUP BY}, for example, may use a
local hash table on one machine but a partial aggregation, shuffle, and reduce path on a
cluster. The SQL semantics are intended to match, but independent implementations create
independent performance behavior and correctness risks. One concrete failure encountered in
\sys{}'s development was a float key that grouped correctly in the local path but split into
two groups after a distributed shuffle.

\sys{} makes that split impossible. A stateful operator may exist only as a mergeable triple,
and the three execution regimes vary only its scheduling (\cref{fig:schedulers}). One core
folds a stream of batches. Many cores partition and merge. Many machines partition, run the
partial pass per node, ship pre-aggregated state, and combine in a tree. Formally, for any
partitioning
$\{p_k\}_{k=1}^{n}$ of an input multiset $P$,
\begin{equation}
\mathsf{finalize}\Big(\textstyle\bigoplus_{k=1}^{n} \mathsf{partial}(p_k)\Big)
  \;=\; \mathsf{finalize}\big(\mathsf{partial}(P)\big),
\label{eq:merge}
\end{equation}
where $\bigoplus$ folds the per-partition states under the operator's combine. This holds
exactly when the operator factors into $\mathsf{partial}\colon \mathcal{M}(R) \rightarrow
S$, $\oplus\colon S \times S \rightarrow S$ and $\mathsf{finalize}\colon S \rightarrow
\mathcal{M}(R')$, with $\mathcal{M}(\cdot)$ a multiset, $(S,\oplus)$ a commutative monoid,
and $\mathsf{partial}$ a monoid homomorphism from $(\mathcal{M}(R), \uplus)$ to
$(S,\oplus)$. Each law earns its keep --- associativity buys any tree shape, commutativity any
arrival order, the identity the empty partition --- and together they make the partition count
a free variable. That is the whole of the claim: one core, many cores and many machines are
three values of it. \cref{eq:merge} is a property test and not a comment, asserted over
generated random partitionings against the single-pass result.

One qualification belongs with \cref{eq:merge} rather than in a footnote, because
overstating it would make the invariant unfalsifiable. Row multisets, column names and
column types are exact under any partitioning, but floating-point reductions are
identical only \emph{up to reassociation}: $\mathsf{combine}$ is associative in exact
arithmetic, IEEE addition is not, and the partition count fixes the summation order.
Neumaier compensation and Chan's parallel formula for variance hold that error near the
last bits; nothing can remove it while the partition count is free.

Two consequences follow. \textbf{There is no distribution tax on the small case},
because distribution is a scheduling decision made per query rather than a runtime you
start; and \textbf{there is no rewrite on the way out}, because the operator that wins
on one core is the one that runs on eight nodes.

\subsection{Relationship to existing algebraic interfaces}

The algebra itself is established. Gray et
al.'s algebraic aggregate~\cite{gray1997datacube} and MapReduce's
combiner~\cite{dean2004mapreduce} are important precedents,
Summingbird~\cite{boykin2014summingbird} made monoids the explicit unifying device, and
the Dataflow model~\cite{akidau2015dataflow} generalized batch and streaming into one
specification whose \texttt{CombineFn} has the shape of our triple. What we claim is the
policy, and the difference is the word \emph{only}. In each of those systems
mergeability is an \textbf{opportunity}: a library interface an operator may implement
to run better, alongside a general execution path for everything that does not, so the
fork survives one level down --- in the two engines Summingbird compiles onto, or in the
runner Beam hands its specification to --- and that is where the divergences and the
second set of bugs live. Here mergeability is an \textbf{admission criterion} for the
engine's own operators: there is no general path to fall back to and no second runner
underneath, so no second implementation can exist to drift from the first. That is a
stronger claim and a more expensive one, and \cref{sec:price} is the trade-off.

\subsection{Scope and excluded operator classes}
\label{sec:price}

A restriction is only interesting if something falls outside it, and \cref{tab:vocab}'s
last two blocks are the list. \textbf{Exact order statistics} are not algebraic
aggregates, because the state is the input; \sys{} admits the mergeable approximation (a
KLL sketch~\cite{karnin2016kll}) and computes the exact form by falling back to a sort.
\textbf{A global sort, a \texttt{rank()} over a total order and a recursive fixpoint}
have no commutative combine, and no amount of design gives them one, so they are
admitted under the weaker range-partitionable contract instead: the single algebra
covers the stateful operators, not literally every operator.

\textbf{Operators we can express but cannot yet distribute.} The inequality join is the
honest case, and it is a live cost rather than a historical one. IEJoin's sweep over a
sorted union has no mergeable decomposition without the block-pair pruning
of~\cite{khayyat2015iejoin}, so today the distributed planner executes the operator whole.
It satisfies single-node $=$ distributed by not distributing, which satisfies the letter of
the invariant and not its spirit (\cref{sec:limitations}).

\textbf{Algorithms we declined.} A hash join that builds a shared global table across
workers, and a streaming state backend with tombstones, have no mergeable form we could
find; the first is why the join build side is replicated rather than shared, and the second
is why the incremental checkpoint below is restricted to operators whose state never
shrinks. Neither was added.

The restriction therefore has concrete costs: one operator class remains undistributed,
one exact aggregate falls back to a sort, and two implementation strategies were rejected.
These exclusions define the scope of the design and make the trade-off explicit rather than
hiding it behind a fallback execution path.

\subsection{Reusing operator state for batch and streaming}
\label{sec:streaming}

The constraint that settles the scale split settles this one too, because the mergeable
triple \emph{is} the incremental form. An aggregate that folds each batch through
$\mathsf{partial}$ and $\mathsf{combine}$ never reads its whole input, which is exactly
what a continuous query needs: state that updates per arrival and finalizes on demand. The
operator a batch query uses and the operator a continuous query needs are not two
implementations that happen to agree. They are one implementation, and the difference is
whether anything ever calls $\mathsf{finalize}$.

\sys{}'s executor is therefore a streaming executor for \emph{every} query. Operators
pull small batches through a pipeline and materialize only at breakers, so peak memory
is the breakers' state plus one batch per worker: a constant, independent of how much
data arrives. On \sys{}'s own join-heavy q3/q4/q5 shape, same query and same engine, the
streaming path holds 3.4\,MB at one million rows and 3.3\,MB at four million where the
materializing path takes 198\,MB and 794\,MB. A bounded Parquet input and an unbounded source can therefore execute the same operator
implementations under the same per-worker buffering model; long-running state size still
depends on the admitted operator and is subject to the limitations in \cref{sec:limitations}. The one place an incremental operator still costs something is the checkpoint,
and the algebra pays there too: recording the \emph{partial} each micro-batch folded in
is linear where snapshotting the whole state is quadratic in the epoch count, and it is
sound because a base plus every partial after it \emph{is} the state. We do not claim
Flink's guarantees~\cite{carbone2015flink}: \sys{}'s streaming is a micro-batch driver,
and \cref{sec:limitations} states exactly which guarantees that forecloses.

    .join(cat, on="sku")
    .group_by("label")                  # mergeable
    .agg(n=bt.col("sku").count()))

hot.collect(distributed="auto")         # the only scale knob
\end{lstlisting}
\caption{A \sys{} program. Decode, inference, join and aggregation are nodes in one
logical plan, so the optimizer sees the filter and the decode together and runs the
cheaper one first; nothing here is a user-defined function, and Python never touches a
row. The last line is the only place scale appears: \texttt{distributed} changes which
schedulers of \cref{fig:schedulers} run, not which operators and not the answer.}
\label{fig:program}
\end{figure}

The historical bargain was that SQL is restrictive and therefore optimizable, while a
user-defined function is expressive and therefore opaque. That bargain fails when the
practitioner writes Python by default, because the natural way to express a
transformation becomes a per-row callback the optimizer cannot reorder or push a
predicate through. \sys{}'s answer has three parts, in order of preference, and
\cref{fig:program} exercises all three.

First, make the UDF unnecessary. The public surface is a Python \emph{expression} API
--- \texttt{col("x") * col("y")}, \texttt{.str.contains(...)},
\texttt{.list.cosine\_similarity(...)}, \texttt{.image.to\_tensor(...)},
\texttt{.audio.mel\_spectrogram(...)} --- and every one lowers to the same
\texttt{bc\_expr::Expr} the SQL front-end produces, so it is optimized, JIT-eligible and
executed in Rust. That is what makes the filter in \cref{fig:program} movable below the
decode: both are plan nodes with costs, not opaque calls. Second, when a callback is
genuinely required, make it batch-first: a \sys{} UDF receives a whole Arrow
\texttt{RecordBatch} and returns one, and a class-based UDF keeps a loaded model or a
connection across batches and executions, which is what makes session-warm GPU pools
possible. Third, keep SQL, which parses to the same \texttt{LogicalPlan} and runs the
same rules and kernels. Neither surface wraps the other, because both lower to one plan.

A \texttt{Dataset} is a lazy, immutable handle to that plan: every operation returns a
new one and nothing executes until a terminal call, which is what lets the scale
decision sit on the last line rather than in the constructor. It is the API-level
statement of \cref{sec:algebra}: the program does not know how many machines will run
it.

% ===========================================================================
\section{Measurement-driven optimization}
\label{sec:learning}
% ===========================================================================

An engine that cannot price its data or its operators before running can keep inventing
numbers, which is what a static cost model does, or it can measure itself and plan from
what it saw. The shared operator implementation gives measurements a stable semantic identity across
execution modes. In particular, observed cardinalities and result-equivalent strategy outcomes
can be reused when the same logical operator is later scheduled with a different partition
count. Runtime cost measurements still depend on the execution environment, but they no longer
refer to distinct local and distributed implementations. \sys{} uses this history to augment
static estimates rather than treating shipped constants as the only source of planning
evidence.

A single rule keeps this safe. \textbf{Every learned value is result-invariant.} Each
bandit arm emits the same relation, a threshold picks between equivalent algorithms, a
partition count only shards. Learning changes how much memory a query reserves, when it
spills, how wide a batch is, and which of several equivalent algorithms runs. It can never
change the answer, and that is property-tested: a cold store reproduces the untuned engine
byte for byte, so the worst a stale value can do is cost throughput. This is a deliberately
different bet from learned optimizers that predict
plans~\cite{marcus2019neo,marcus2021bao,kipf2019learned}, which change which plan runs in ways
that are hard to bound. A weaker signal buys a far stronger safety property, and that
is what lets the feature ship on by default.

\paragraph{Three clocks, not one.} Adaptive query processing usually means one thing:
re-plan at a stage boundary. \sys{} does that too, and it is the least interesting of the
three places it adapts.

Two of the clocks run \emph{inside} an operator, at microsecond grain, and both replace
a number a static model would have to invent with one the operator just observed. A
conjunctive filter orders its predicates by measured time-per-row over fraction-removed
rather than by static cost, which matters because cost is not selectivity, and two
predicates of identical cost where only one is selective is a case a static model cannot
fix even in principle ($1.86\times$ on the adversarial shape). A parallel aggregate
chooses between per-morsel hash tables and pre-partitioning by key from the reduction a
sample of morsels actually achieved rather than from a distinct-count estimate
($3.7\times$ when grouping reduces nothing). The second matters architecturally rather
than numerically: pre-partitioning \emph{is} the right-hand panel of
\cref{fig:schedulers} executed across cores instead of machines, so the high-cardinality
single-node aggregate is the distributed algorithm chosen at runtime. Refusing to fork
the operator did not only delete a class of bug; it handed the single-node executor a
second strategy for free.

The outer two clocks are familiar. At a pipeline breaker the engine re-plans the
remainder on real cardinalities --- the same mechanism and granularity as Spark
AQE~\cite{sparkaqe}, and we claim no finer grain, though it runs single-node where AQE
needs shuffle stages. Across executions the engine accumulates sketches, refits cost
coefficients and converges bandits, which \cref{sec:eval-learning} measures. Each clock
reads only what has already been measured, so none is a prediction.

% ===========================================================================
\section{Multimodal and heterogeneous execution}
\label{sec:pipeline}
% ===========================================================================

The second fragmentation is a grid rather than a line: engines specialize by the
\emph{shape} of the data and by the \emph{tier} of the model, the two axes fragment
independently, and a team lands in the cross product. The systems evaluated here occupy different points in this design space. DuckDB and Polars
focus primarily on structured analytical execution; Ray Data and Daft provide multimodal data
paths; and Spark commonly exposes custom media/model logic through user-defined functions. The
comparison of interest is therefore not feature count but whether decode and inference are
visible to the same optimizer that reasons about surrounding relational operators.

\sys{} exposes a broad set of source formats and ML operations, from classical models through
GPU inference and LLM batch generation. The relevant design property is not the number of API
entry points but that a single logical plan can span them, because preparing
data for a model is not a different kind of work from querying it. Image decode, crop
and normalization to a tensor are Arrow kernels in the data plane, not a Python UDF, and
so are audio decode, resampling, mel-spectrogram and MFCC --- the last two matched to
\texttt{torchaudio} within $10^{-6}$ and, across the comparator set of \cref{sec:eval},
without an in-engine equivalent anywhere else. So are vector distances and embedding
pooling. Two measurements bound what that is worth on the axis both sides run natively:
against Ray Data's \texttt{read\_images} over the same corpus \sys{} decodes
$6.4$--$6.6\times$ faster, entirely the difference between an engine expression and a
per-batch Python UDF, and against Daft on the shared ingest path it leads by
$1.9\times$, rising to $5.7\times$ on a pass Daft expresses as a per-row callback.

\paragraph{One scheduler across CPU and GPU.}
\label{sec:gpu}
Run a chain of unlike costs --- I/O, then CPU decode, then a forward pass, then a CPU
join --- inside one worker and the accelerator idles through every decode; the usual
remedy is for the user to hand-tune a ratio of CPU workers to GPU workers, per stage.
\sys{} treats it as a scheduling problem the engine owns: a plan carrying a resource-
class boundary is split there, a pool of CPU producers decodes and preprocesses, a pool
of GPU consumers runs the model, and Arrow batches move between them over the same
credit-bounded Arrow Flight~\cite{arrowflight} transport the shuffle uses, so a slow
consumer applies backpressure instead of accumulating. Both stages run the identical
sub-plan through the ordinary executor; only the placement differs, which is what keeps
the split from becoming a second semantics.

Ray Data's streaming batch model~\cite{luan2025streamingbatch} attacks the same problem
and is the work to compare against rather than the baseline to beat. Making the
\emph{partition} the unit of execution buys it elasticity and partition-level fault
tolerance, neither of which \sys{} has. What \sys{} buys instead is what that model does
not attempt: both stages are the \emph{same relational plan} under the \emph{same cost
model} as the joins around them, so the optimizer can push a filter below a decode
because it sees both. The comparison is therefore a trade-off rather than an unqualified win, and
\cref{sec:eval-dist} measures the half we are weaker on.

\sys{} is a Python control plane over a Rust data plane, with Arrow
\texttt{RecordBatch}~\cite{arrow} the only columnar contract at every internal boundary
and across the FFI. Python builds a plan, optimizes it and ships it down as JSON; data
returns zero-copy through the Arrow C Data Interface, and Python never iterates a row.
That boundary is what makes a Python surface affordable: the control plane's cost is per
\emph{query}, so seven phases of rules iterated to a fixpoint cost single-digit
milliseconds because nothing in them is per-row (\cref{sec:smallquery}).

Three structural rules do the load-bearing work, and each exists because its violation
is silent. \emph{The subsystems may not import one another.} \kyber{} decides, \carbo{}
protects, Core measures, and a lint contract forbids any edge between them, which reads
as bureaucratic until you see what it prevents: an optimizer pass that starts collecting
its own telemetry, or an executor path that starts making optimization decisions,
compiles and passes every test while quietly corrupting the feedback loop the design
depends on. The only sound edge is the one through the Metadata Hub in \cref{fig:arch},
and it is directed --- measurements flow out of execution into planning, never back.
\emph{One expression type serves every execution tier.} An interpreter is the
correctness oracle and a Cranelift~\cite{cranelift} compiled fast
path~\cite{neumann2011compiling} consumes the \emph{same} expression, so it must be bit-
for-bit identical on the subset it supports and fall back silently otherwise; a
divergence --- one tier wrapping an integer overflow where the other raises --- is
invisible in any single result, because which tier ran depends only on whether the
expression happened to compile. \emph{The crate dependency graph points one way}, from
the Arrow layer up through one expression type and one relational plan type to the
interpreter, so a new backend cannot introduce a second definition of what a plan node
means. Underneath all three the executor pulls small batches through linear runs of
operators and materializes only at pipeline breakers~\cite{leis2014morsel} --- which is
exactly where the middle clock of \cref{sec:learning} re-plans.

\paragraph{\kyber{}, the optimizer.}
\label{sec:kyber}
\kyber{} is a fixed sequence of phases over the plan, and the architecturally
interesting property is not the rule count (726 at the commit these results were taken
on) but the \emph{ordering of evidence}. Estimation starts from Selinger-style
selectivities~\cite{selinger1979access} and is superseded, in a fixed order, by exact
file footer metadata, then by sketches built during execution
(HyperLogLog~\cite{flajolet2007hyperloglog}, KLL~\cite{karnin2016kll}, Count-
Min~\cite{cormode2005countmin}), then by measured cardinalities filed under a plan
signature, with a bandit~\cite{auer2002ucb} over result-equivalent physical strategies
on top. Every sketch is mergeable under a fixed seed, so one built per partition merges
identically to one built on a single node --- \cref{sec:algebra}'s algebra applied to
statistics, and the reason a distributed run's evidence is admissible to a single-node
plan. Every number also carries \emph{where it came from}, because two rewrites can
corrupt a result rather than merely slow one and are gated on exact provenance, while
everything else may consume an estimate whose worst outcome is a slower plan. A
generator holds the rule set to result-preservation, and the suite carries a second
obligation this design introduces: a learned component can be entirely \emph{inert}
while every answer stays correct, so a test must assert that the learning happened and
not only that the answer did.

\paragraph{\carbo{}, the resource manager.}
\label{sec:carbonite}
\carbo{} decides whether a plan is feasible, hands out memory reservations and shuffle
credits, and decides when a query goes out of core; it never rewrites a plan and never
computes a result, and that restriction dictates its interface. Conventional admission
control answers a boolean, which is useless to a planner because it names no smaller
thing to try, so \carbo{} returns the binding constraint, the \emph{operator} that
binds, and a counter-offer \kyber{} can re-plan around --- precisely because the layer
that may rewrite the plan is not this one. Flow control is credit-based, one credit
being one in-flight batch slot, so a channel's window is a direct bound on its memory
rather than an estimate of it, and the same transport carries the shuffle and the CPU-
to-GPU hand-off of \cref{sec:gpu}. Bulk data never enters the Ray object store, which is
what keeps distribution a scheduling concern rather than a serialization one.

\paragraph{How \sys{} compares.}
\label{sec:differs}
\textbf{DuckDB}~\cite{raasveldt2019duckdb} is the single-node bar: vectorized in the
MonetDB/X100 lineage~\cite{boncz2005monetdb}, a compressed native store with zone maps,
optimized once before execution, and it does not distribute.
\textbf{Spark}~\cite{zaharia2012rdd,armbrust2015sparksql} distributes, and its Adaptive
Query Execution~\cite{sparkaqe} re-plans on measured statistics at stage boundaries.
\textbf{Ray Data}~\cite{luan2025streamingbatch}, on Ray~\cite{moritz2018ray}, is a
streaming batch runtime for ML pipelines with actor pools for GPU work and no relational
optimizer; we benchmark against it throughout because a data engine claiming to serve AI
workloads should be held to the standard of the runtime those workloads use today, which
makes it a yardstick rather than a rival. \textbf{Daft}~\cite{daft} and
\textbf{Polars}~\cite{polars} are native Rust engines over Arrow~\cite{arrow}. \sys{}
does not lead because its kernels are faster than everyone else's; on several axes it is
at parity, and on storage it is behind, because a compressed, dictionary-encoded, zone-
mapped format is exactly what \cref{sec:algebra}'s Arrow-only contract forecloses. Its main architectural distinction in this comparison is the cross-execution measurement
loop: cardinalities, cost coefficients, physical-strategy outcomes, and memory observations
from prior executions can feed later planning decisions. A further difference is the internal data path. \sys{} keeps Arrow-compatible columnar
batches across its operator boundaries, avoiding a format conversion at those boundaries. The
Spark configuration evaluated here carries a substantially higher fixed per-query cost
(\cref{tab:tpch}); this experiment does not isolate how much of that difference comes from
serialization, scheduling, the JVM execution stack, or local-mode overhead, so we do not
attribute the full gap to any one mechanism.

\subsection{Cross-scheduler correctness}
\label{sec:eval-algebra}

The primary claim in this subsection is semantic rather than performance-oriented, so its
main evidence is cross-mode equivalence testing rather than latency. \cref{eq:merge} is property-tested over random partitionings, and an
integration test asserts that single-node equals multi-partition. An operator matrix
then crosses every execution mode with every value edge, because the defects that reach
production here are a non-default flag on a non-default path: a descending sort returned
unsorted data under spill, and a distributed \texttt{GROUP BY} on a float key split one
group in two, and both passed every single-axis test.

Two measurements go further than the test suite, because a generator only ever produces the
case the algebra was designed for. \textbf{The whole suite, through both schedulers}: every
TPC-H query was executed twice on the same box, once through the single-node executor and once
through the distributed one, and compared as row multisets. \textbf{All 22 agree.} Distribution charges a geometric-mean $28.3\times$ at sf1, which is the correct answer
for a six-million-row table on one machine and why the engine's \texttt{auto} policy
declines it at this size. The claim is not that distribution is free; it
is that it is a per-query decision whose price is visible, and that taking it does not change
the answer. \textbf{And a partitioning nobody planned}: a worker dying mid-query leaves the
surviving partials to be recombined in an order and a grouping no planner chose, which
\cref{sec:eval-dist} injects across five fault configurations, with every recovered
relation equivalent to the single-node answer under the comparison stated below. A system carrying a second distributed implementation would have to get
that path right in that implementation too.

The harness gates timing on result correctness. In these runs, Daft does not match the
reference result for TPC-H q6 at either scale, and Polars cannot parse eight of the 99 TPC-DS

Three rows merit additional context. \textbf{TPC-DS} is registered as the full 99-query
suite rather than as a curated subset; 98 queries contribute to the paired timing row in
\cref{tab:breadth}, and the excluded query is q67 for a reason that belongs to the harness
rather than to either engine. The harness's shared loader casts every \texttt{DECIMAL}
column to \texttt{float64} so that all engines read one input type, and q67 ranks a
\texttt{SUM} over a \texttt{ROLLUP}. The two engines reassociate that floating sum
differently, in the last bits, and \texttt{rank()} converts a last-bit difference into a
different \emph{integer} --- which no float tolerance can absorb. Re-run against the source
\texttt{DECIMAL} types both engines support natively, all 100 rows match exactly and in
order and the sum agrees to the cent, so the disagreement is the comparison's rather than a
result defect. The exclusion is symmetric: the gate reports no timing for \emph{any} engine
on a case it fails, so q67 contributes to no engine's ratio. The cast stays in place because
removing it changes every column type in every TPC-H and TPC-DS query, and so every timing
in this paper --- a methodology change to make deliberately and re-measure, not a patch to
apply to one query.
\textbf{The Join Order Benchmark}~\cite{leis2015goodjoin} is directly relevant to the paper's
measurement-driven planning thesis and is a suite \sys{} loses. Its IMDb workload contains
correlated predicates for which classical independence assumptions can produce inaccurate
cardinality estimates; Leis et al.\ use the benchmark to show how strongly such estimation
errors can affect plan quality. \cref{sec:limitations} explains why \sys{}'s mechanism for
feeding measured cardinalities back into this workload is currently ineffective.
\textbf{H2O.ai}~\cite{h2obenchmark} isolates operators that TPC-style suites embed inside larger
plans. Here \sys{} leads the join task and trails the group-by against DuckDB's native store;
the group-by keys are low-cardinality strings that DuckDB stores dictionary-encoded, whereas
\sys{} reads full Arrow \texttt{Utf8}. On identical Arrow input, the same group-by suite is
$0.089\times$ and 10 of 10.

\subsection{Separating storage representation from execution}
\label{sec:eval-opmix}

The operator mix of \cref{tab:breadth} holds everything but the one variable fixed: one input representation, one machine, no SQL
front-end differences, no scan in the timed region, and DuckDB present twice differing
\emph{only} in whether it was allowed to ingest that identical Arrow input into its own
compressed store first. Across the 19 cases, \sys{} is faster in 15 comparisons against DuckDB-on-Arrow and in 12
comparisons against DuckDB's native store. The difference between those two configurations
shows that physical representation materially changes the result; it should not be interpreted
as a pure kernel comparison.

The four \sys{} loses to DuckDB-on-Arrow are the informative ones, because they are the only
cases where the input is genuinely equal and \sys{} is still behind: three string sorts and a
high-cardinality \texttt{DISTINCT}. Arrow's \texttt{Utf8} keeps a string's bytes in a
separate buffer behind a 32-bit offset, so ordering one is a gather through an indirection
where DuckDB compares a 16-byte value with its first bytes inline --- the German-string
representation Umbra introduced~\cite{neumann2020umbra}. That is a data-layout gap in the
columnar format rather than in either engine, and it is the gap the H2O group-by result
attributes to storage. It is measurable directly: grouping a dictionary column is about
$7\times$ faster than grouping the decoded one, so handing \sys{} DuckDB's own representation
across the FFI makes it \emph{slower}, because the boundary decodes it to satisfy the
Arrow-only contract. A change that would have let a dictionary reach the kernel was built,
measured and reverted for regressing plainer shapes. This is the one place where the paper's
central constraint is paid for in performance rather than repaid.

On ClickBench~\cite{clickbench}, the same pattern appears at suite scale: \sys{} is faster
on all 43 queries against DuckDB on identical Arrow input and also leads the native-store
comparison, but by a smaller margin. Together with the operator-mix experiment, this supports
the narrower conclusion that storage representation accounts for a substantial part of the
observed gap; it does not establish that all remaining differences are attributable to storage.

\subsection{CPU cost in addition to wall-clock latency}
\label{sec:eval-cost}

The preceding ratios measure wall-clock latency, which does not by itself measure compute
consumption. An engine can reduce latency by using more parallel CPU time, so we report both
metrics for the in-process TPC-H comparison. It is measurable here for a specific reason: \sys{}
and DuckDB both execute in-process, so \texttt{getrusage} charges both engines' threads to one
counter and the delta across a call is that engine's CPU time. On TPC-H sf1, all 22 queries,
gated on correctness before timing: \textbf{\sys{} buys a $1.3\times$ wall-clock win with
$1.9\times$ the CPU, by running on $2.4\times$ the cores} --- geometric-mean $0.78\times$ wall
against $1.86\times$ CPU, at 21.9 effective cores against DuckDB's 9.2, excluding the one
query answered from a recorded statistic rather than executed. The wall figure reproduces
\cref{tab:tpch}'s $0.79$, which cross-checks that this is the same engine.

This result bounds the latency claim. If otherwise-idle CPU capacity has low marginal cost,
the lower wall-clock time may be desirable; when CPU time or energy is the constrained
resource, the higher compute consumption can dominate the decision. Neither engine saturates
the machine --- DuckDB remains below ten effective cores of 96 vCPUs in these runs --- so
part of the latency difference reflects how much parallelism each engine extracts rather than
per-core efficiency alone.

\paragraph{Cold and small-query latency.}
\label{sec:smallquery}
\cref{sec:algebra}'s first consequence is that a small query pays no distribution tax, and a
suite reporting best-of-$N$ warm timings structurally cannot check it, because such a suite
never sees a shape for the first time --- which is what a user issues constantly. Measured
separately, with a fresh literal per iteration so the plan cache cannot hit, optimizing a
never-seen filter\,$\rightarrow$\,join\,$\rightarrow$\,group-by costs $2.75$\,ms, and end to
end over twelve never-seen shapes at $n=10^4$ \sys{} runs at $0.80\times$ DuckDB on a cold
filter and $0.27\times$ on a cold \texttt{count(*)}. DuckDB also pays a first-query cost, and the measured cold-start overhead does not erase
\sys{}'s advantage on these two shapes. A warm gap remains on the narrowest case: 4.07\,ms
versus 2.04\,ms. Only 0.002\,ms of the \sys{} time is attributed to planning, indicating that
the residual fixed cost lies elsewhere in the per-query execution path, including the FFI
boundary.

\subsection{Streaming throughput and driver overhead}
\label{sec:eval-streaming}

Two measurements test the shared-operator claim from opposite directions.
\textbf{Against a streaming engine}, draining a four-million-row
Parquet backlog through a grouped aggregation, correctness-gated, \sys{} runs at 18.9M rows/s
against Spark Structured Streaming's~\cite{armbrust2018structured} 6.0M --- a $3.2\times$ lead
--- under the memory bound flat in the input reported in \cref{sec:streaming}.
\textbf{Against a batch engine}, DuckDB answers that same
aggregation in 15.9\,ms as a one-shot query, $13\times$ faster than \sys{}'s streaming path.
That gap is not the operators, which are shared and are the paper's claim; it is the
streaming \emph{driver}, which plans a micro-batch, commits offsets and writes a checkpoint
per trigger while a batch query does none of those things. What this supports is that the
operators are one implementation and the memory bound holds for both, not that a streaming
query is as cheap as a batch one. It is not, by an order of magnitude, and the cost is the
driver.

Aggregate all-to-all shuffle throughput on an 8-node Ray cluster is 2.0\,GB/s at two worker
nodes, 6.9 at four and 15.2 at eight --- superlinear, $7.6\times$ for $4\times$ the nodes. The
mechanism is the algebra: mappers publish pre-aggregated state rather than rows, so adding a
node adds reduce capacity instead of contention, and a combiner tree plus credit-based flow
control keeps per-node memory bounded as the cluster widens. Two qualifications belong with
that number rather than after it. A \emph{single} reducer stays pinned at its NIC
($\sim$2.7\,GB/s), so the gain is in the aggregate and not in any one channel; and at two
nodes the shuffle does not saturate the available reduce capacity, so part of the 2-to-4 gain
is recovered inefficiency rather than scaling. The shape is what we stand behind --- nodes add
throughput at no per-node memory cost --- not $1.9\times$ per doubling forever. Distribution
is also not always the right answer, and the engine says so: forcing
\texttt{distributed=True} on in-process data costs 1.9--4.5\,s a query, which is exactly the
tax \cref{sec:algebra} exists to make optional.

Throughput alone does not characterize distributed execution; recovery behavior is also
part of the design. \cref{tab:faults} injects the failure directly. Five fault-injection arms, two failure phases, up to two simultaneous losses, and every recovered
relation equivalent to the single-node answer --- the assertion \cref{eq:merge} is for, tested
against real failures rather than random partitionings. Recovery is also parallel across losses, since two workers lost costs what one costs,
which falls out of the algebra too: what is regenerated is a partial, and partials
regenerate independently. Replication, however, makes recovery worse. Copying every
published bucket to a survivor is meant to convert a recompute into a re-fetch; instead
it turns a $2.84\times$ recompute into an $8.40\times$ recovery. The environment is a
confound --- replication's premise is that re-reading the source from object storage
dominates, and on a single box with an in-memory source that premise is false --- so the
measurement does not refute the design. It establishes that the benefit is unproven in
every environment this system has been measured in, and that the fixed cost is real.

\subsection{GPU and ML workloads}
\label{sec:raydata}

Ray Data is the most relevant comparator in this evaluation because it is designed for
streaming batch execution of ML and GPU pipelines. On 8$\times$T4 with real models, \sys{}
measures $2.05\times$ higher throughput on ResNet-50 batch inference, $1.98\times$ on image
embeddings, $1.96\times$ on fractional-GPU packing, $3.6\times$ on video-clip inference, and
$3.0\times$ on training-data ingest (\cref{fig:headline}, right). Larger ratios for audio
feature extraction ($12.5\times$), LLM batch inference ($11.1\times$), and text embeddings
($47\times$) primarily reflect scheduling and batching choices rather than faster model
kernels, so we do not generalize from them. On a sufficiently large compute-bound job, both
systems saturate the same GPU and converge to parity. The measured result is therefore that
integrating these operators into the relational plan did not impose an observable throughput
penalty on the tested workloads; it is not evidence of universally faster GPU kernels. These ratios
are also only meaningful if the comparator is configured properly, and ours initially was not:
our adapter registered each table as a single block, which is Ray Data's unit of parallelism,
so a 6M-row table ran on one execution slot out of 96. That was our defect, and every number above is from
the corrected adapter.

\section{Limitations and threats to validity}
\label{sec:limitations}
% ===========================================================================

The preceding experiments span several workload classes, but they do not establish uniform
superiority. This section separates known system limitations from threats to the validity and
generality of the measurements.

\paragraph{Storage is the largest open gap, and it is structural.} \sys{} owns no
storage format: Arrow is the only columnar representation any operator sees, which
forecloses a compressed, dictionary-encoded, zone-mapped store and a German-string
layout~\cite{neumann2020umbra} in one stroke. Three results above reflect that decision --- TPC-H at sf10 ($1.29\times$), the H2O group-by ($1.19\times$), and the string
sorts that lose even on identical input --- and closing it needs a plan's logical type
separated from a morsel's physical one, an architectural change rather than a kernel
one. The scan path is a second, independent term: \sys{}'s Parquet decode costs
$1.7$--$3.0\times$ DuckDB's CPU, which places it in the Arrow Rust decoder rather than
in anything specific to this engine.

\paragraph{The learned loop does not yet improve the benchmark most sensitive to estimation error.} The Join
Order Benchmark remains $1.29\times$ behind, and the mechanism this paper argues should
close it is inert on the shape that matters: the key a measured cardinality is filed
under and the key the estimator reads back disagree for the commonest aggregate shape,
so the loop writes a true row count that nothing consumes. The defect also exposes a broader calibration issue: correcting the key alone makes the engine \emph{slower}
--- TPC-DS moves $0.965 \rightarrow 0.988$ and JOB $1.252 \rightarrow 1.293$ --- because
every threshold downstream of that input was calibrated while it was an order of
magnitude low. A learning loop is a closed system, and repairing one edge is a
recalibration rather than a patch; it is pinned as a failing test, not described as
done. A second limit sits on the positive result: the $2.4\times$ first-execution
premium of \cref{fig:learning} folds the plan cache together with the learned store. The
experiment that would separate them is a three-arm ablation --- plan cache on with the learned
store cold, the learned store warm with the plan cache disabled, and both on --- and it has not
been run, so the paper reports the premium end to end and attributes it to neither half.

\paragraph{Streaming is micro-batch, and does not reach Flink's guarantees.} There is no
operator graph, no barrier protocol and no keyed state backend; the driver is a Python
loop over pull, execute, write, and a single point of failure with no standby.
Watermarks do not propagate across operators because there is no graph to propagate
along, and streaming state is one in-memory Arrow batch that does not spill. The driver
is also expensive in absolute terms (\cref{sec:eval-streaming}), so the shared-operator
claim buys maintainability and a memory bound, not streaming performance competitive
with a one-shot query. Exactly-once holds for Delta, for a file sink by batch position,
and for a \emph{keyed} database write; an \texttt{append} to Iceberg or Hudi writes its
rows twice on a replayed epoch.

\paragraph{Recovery is correct in the tested cases, but replication is not yet beneficial.} Correctness under worker loss holds across every arm tested, which is the
property the algebra is for; the performance half does not, and the one environment we
can measure it in is also the one most hostile to its premise. Replicas are resident
rather than on a durable tier, and \sys{} has no equivalent of Spark's external shuffle
service, so a whole-node loss that takes every copy still costs a recompute round. The
economics therefore remain untested where they are supposed to hold: repeating at least the
two reduce-phase arms across separate machines, reading from object storage over a measured
network, is what would decide whether replication pays, and no such run exists here. Two
operator-level ceilings stand as well: the CPU-to-GPU split happens at exactly one
resource boundary, so a three-stage chain rides its third stage in the consumer, and the
inequality join is not distributed at all (\cref{sec:price}). Finally, \sys{} owns no
storage, so there is no transaction manager, no MVCC and no index --- an engine whose
floor is milliseconds is not a read path an application points transactions at.

\paragraph{Wall clock is not the only currency.} \cref{sec:eval-cost} measures rather
than flags it: $0.78\times$ the wall time for $1.86\times$ the CPU, on $2.4\times$ the
cores. When otherwise-idle CPU capacity has low marginal cost, that trade may be favorable; when
CPU time or energy is the constrained resource, it may not. We report
both and do not net them together.

\paragraph{Threats to validity.} The following factors limit how broadly the benchmark
results should be generalized. \emph{One machine}, and one of them for the distributed results too: the sf1-to-
sf10 attribution is a two-point scaling study and not a scaling law, and the worker-loss
arms run on a single-box local Ray cluster that removes the network replication's
premise rests on. \emph{Warm, best-of-$N$}: the headline suites report the best of
several runs of the same query, which is exactly the shape a memoizing engine wins, and
\sys{}'s session carries a plan cache and a learned-stats loop across those repeats
where DuckDB and Polars have no counterpart. \emph{The comparator pays a conversion
\sys{} does not}: every engine is asked for a \texttt{pyarrow.Table}, and on a query
returning nine million rows that conversion is roughly \emph{half} of DuckDB's measured
time. \emph{The gate compares multisets}, and was blind to whether a sort had happened
at all until the ordered cases were given an ordered comparison. \emph{Comparator
configuration}: we found and fixed one adapter defect that cost Ray Data 95 of 96 cores,
and three in the Spark adapter. \emph{Process}: continuous integration installs neither
Ray nor a GPU, so the distributed and GPU results rest on recorded runs rather than on
the gate that runs on every commit, and therefore have weaker continuous-reproducibility coverage than the single-node CPU results.

\paragraph{What the next evaluation pass owes.} These threats are addressable by measurement
rather than by argument, and naming the experiments is more useful than hedging the prose.
Five stand out. \emph{Dispersion}: report per-query medians with an interval alongside the
minimum, over repetitions in independent processes, so a ratio carries an error bar. \emph{A
cold variant of the headline suites}: a fresh process and an empty learned store for every
timed query, which is the configuration least favourable to this engine and the one a first-time
user meets. \emph{The learning ablation} above, which is the only way to say what the
cross-execution loop is worth on its own. \emph{A multi-node recovery experiment} with
object-storage input, which is the only environment in which replication's premise is true.
And \emph{a published artifact}: the adapters, command lines, configuration and raw per-query
outputs for every table here, so that a reader can re-derive a geometric mean rather than trust
one.

\section{Related work}
\label{sec:related}
% ===========================================================================

\sys{} sits at the intersection of five lines of work, and takes something from each.

\paragraph{Vectorized and compiled single-node execution.} The columnar, batch-at-a-time model
begins with MonetDB/X100~\cite{boncz2005monetdb} and the compiled
alternative with HyPer~\cite{neumann2011compiling};
Umbra~\cite{neumann2020umbra} contributed the inlined-prefix string representation that
\cref{sec:limitations} names as \sys{}'s largest structural gap. \sys{}'s execution is
morsel-driven~\cite{leis2014morsel} and vectorized, with a Cranelift~\cite{cranelift} compiled
path carrying a proven-identical fallback, and DuckDB~\cite{raasveldt2019duckdb} is the closest
single-node comparator. Nearest to \sys{}'s \emph{implementation} choices are the embeddable
Arrow-native engines --- Velox~\cite{pedreira2022velox}, Photon~\cite{behm2022photon} and
DataFusion~\cite{lamb2024datafusion} --- which share the columnar contract and the
library-rather-than-server posture. These systems share important implementation choices with \sys{}, including columnar
execution and embeddability, but they are typically integrated into a larger host system for
features such as distribution or end-to-end query orchestration. \sys{} differs in combining
its operator contract, cross-execution measurement loop, and media/inference expressions in
one engine.

\paragraph{Distributed dataflow and cloud warehouses.} MapReduce's
combiner~\cite{dean2004mapreduce} and Gray et al.'s algebraic
aggregate~\cite{gray1997datacube} are where the mergeable triple comes from; \sys{}'s
contribution is not the triple but the refusal to admit an operator without one.
Spark~\cite{zaharia2012rdd,armbrust2015sparksql} is the direct ancestor of the design
\cref{sec:differs} departs from, the cloud
warehouses~\cite{sethi2019presto,dageville2016snowflake} answer the same scale question
with a service rather than a library, and the lakehouse line~\cite{armbrust2020delta} is
where \sys{}'s table formats come from. Volcano~\cite{graefe1994volcano} established the
operator/exchange separation this paper leans on, and our departure is that there is no
distributed operator to separate.

\paragraph{Streaming and unified execution.} Structured Streaming's framing of a stream
as an unbounded table~\cite{armbrust2018structured} is the framing \cref{sec:streaming} adopts. The
two closest ancestors of this paper's central device are here rather than in the
operator literature: Summingbird~\cite{boykin2014summingbird} made the monoid the
explicit unifying abstraction so that one program compiles to both a batch and an online
engine, and the Dataflow model~\cite{akidau2015dataflow} generalized the two into a
single specification. The difference we claim over both is not the algebra but the
level: they unify the program or the specification above two engines, and we make
mergeability the admission test of one engine's own operators.
Flink~\cite{carbone2015flink} and Naiad~\cite{murray2013naiad} are the dataflow answer,
with the operator graph, barrier protocol and keyed state backend \sys{} does not have
and does not claim, and DBSP~\cite{budiu2023dbsp} derives incremental operators from a
query algebra --- close in spirit to reusing the triple as the incremental form, and
more general.

\paragraph{Adaptive and learned optimization.} Estimation begins with
Selinger~\cite{selinger1979access}; mid-query re-optimization and
eddies~\cite{avnur2000eddies} are the lineage of the stage-
boundary clock, with Spark AQE~\cite{sparkaqe} its closest deployed relative --- the
same mechanism and granularity, which this paper is careful not to overclaim past.
Learned optimizers~\cite{marcus2019neo,marcus2021bao} attack estimation with models that
change which plan runs; \sys{} takes the lighter route of
sketches~\cite{flajolet2007hyperloglog,karnin2016kll,cormode2005countmin}, refit cost
coefficients and a bandit~\cite{auer2002ucb} over \emph{result-equivalent} strategies,
which buys reproducibility and a cold start that is exactly the untuned system, and
gives up the ability to correct a genuinely bad plan choice. Leis et
al.~\cite{leis2015goodjoin} is both the standing argument for measured cardinalities and
the benchmark \sys{} still loses.

\paragraph{Data systems for machine learning.} Ray~\cite{moritz2018ray} and Ray Data's
streaming batch model~\cite{luan2025streamingbatch} are the runtime the AI evaluation is
measured against and the closest system to \cref{sec:gpu}; Daft~\cite{daft} is the
closest multimodal relational engine, and MosaicML's
StreamingDataset~\cite{mosaicstreaming} is where the computed-permutation epoch order
comes from. Putting a model inside the query optimizer is itself established:
NoScope~\cite{kang2017noscope} and BlazeIt~\cite{kang2020blazeit} optimize queries over
neural-network inference with cascades, proxy models and control variates. The
difference is scope rather than ambition --- those systems optimize \emph{around}
inference for a class of query, approximating where the semantics permit it, while
\sys{} makes decode, embedding and inference ordinary expressions in the relational
algebra, exact by construction. Their techniques can provide stronger optimizations for the query classes they target,
whereas \sys{} emphasizes a uniform exact execution model across a broader operator surface.

\section{Conclusion}
% ===========================================================================

\sys{} tests a deliberately restrictive systems hypothesis: many boundaries in modern data
processing can be handled as scheduling and planning choices if the engine refuses to maintain
separate stateful operator semantics for each execution regime. Its admission rule is simple:
a stateful operator must factor into \pcf{} over Arrow, or it must use an explicitly weaker
contract or remain outside the supported distributed path.

The evaluation provides evidence that this restriction is useful but not sufficient on its
own. The same operator implementations produce equivalent TPC-H results through local and
distributed schedulers and remain correct in the tested worker-loss configurations. The same
state representation supports micro-batch execution, and the same logical plan can include
relational, media, embedding, and inference operators. The measurement loop can adapt
result-equivalent physical choices across executions without changing query semantics.

Performance depends strongly on what is held constant. On identical Arrow input, \sys{} is
faster than DuckDB on every suite for which that comparison is available in the harness. When
DuckDB uses its native compressed representation and storage statistics, the result reverses
for TPC-H at sf10. The controlled operator experiments indicate that physical representation
explains a substantial part of that difference, especially for strings and dictionary-encoded
keys, but the current evaluation does not justify reducing all remaining system-level
differences to storage alone.

The costs are equally important. On TPC-H sf1, lower latency comes with $1.86\times$ the CPU
consumption and $2.4\times$ the effective core use. The Join Order Benchmark remains
$1.29\times$ behind. Streaming is implemented as a micro-batch driver with materially weaker
state and fault-tolerance guarantees than Flink-class systems, and replication does not improve
recovery in the environment measured here. These are not peripheral caveats; they identify the
work required to test whether the mergeability-first design remains compelling as storage,
streaming guarantees, optimizer calibration, and distributed recovery mature.

The broader result is therefore narrower than ``one engine wins every workload.'' A single,
mergeable operator vocabulary can remove several implementation forks while remaining
competitive across relational and AI-oriented workloads. The next question is whether the
same property continues to hold once the system gains richer physical representations and
stronger distributed state management without reintroducing the semantic duplication the
design was intended to avoid.

\paragraph{Reproducibility.} Each reported experiment is produced by a named benchmark
script in the committed harness: \texttt{benchmarks/run.py} drives the engine adapters and
\texttt{harness.py} enforces the correctness gate, with \texttt{scenarios/cost\_bench.py},
\texttt{cluster/robustness/worker\_loss.py}, \texttt{scenarios/streaming\_throughput.py},
\texttt{scenarios/learning\_curve.py} and \texttt{scenarios/scheduler\_equivalence.py}
producing \cref{sec:eval-cost}, \cref{tab:faults}, \cref{sec:eval-streaming},
\cref{fig:learning} and the two-scheduler agreement of \cref{sec:eval-algebra} respectively.
The harness refuses to time a debug build or a loaded box, and every result document opens
with a machine fingerprint --- host, CPU model, cgroup-available and logical core counts,
memory, kernel, Python, engine and build profile, git commit, and the exact command line ---
because this project has already published ratios taken across four different machines as if
they were one series. A result therefore cannot silently be attributed to a different build or
a different box, which is a weaker property than a released artifact and is not a substitute
for one.
