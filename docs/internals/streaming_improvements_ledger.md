# Streaming improvements ledger

A running record of improvements, fixes, and features that make Batcher better at
**streaming workloads** — the continuous/unbounded micro-batch engine (triggers, output
modes, watermarks, windowed and stateful aggregation, checkpoint/recovery, streaming
sources and sinks) and the Tier-0 morsel-streaming executor beneath the batch path.

Each entry is a distinct, tested change. Entries are numbered `S<n>` continuously and never
reused, so the count is a count of *distinct* improvements. Category tags:
**bug** (wrong result / data loss), **robustness** (crash/leak/hang on a reachable path),
**feature** (new capability or Spark-parity gap closed), **validation** (fail-fast on bad
input), **perf**, **test** (coverage that pins a contract), **hygiene** (dead code / dedup),
**docs**.

This page is not published (`exclude_patterns` in `docs/conf.py`); it is a working index for
anyone touching the streaming subsystem.

## Control-plane value types and query lifecycle (`plan/streaming`, `api/streaming`)

| # | Cat | Improvement |
|---|-----|-------------|
| S1 | bug | `parse_interval_seconds` accepted a non-finite duration: `nan < 0` is False and `inf` is "non-negative", so both slipped past every check. A NaN trigger cadence makes `remaining > 0` always False and busy-loops the micro-batch thread; an infinite watermark lateness overflows the microsecond literal it lowers to. Now rejected with a `PlanError` at the one gate every duration flows through (`plan/streaming/spec.py`). |
| S2 | robustness | Two active streaming queries under the same explicit `name=` silently evicted the first from the `bt.streams` registry while it kept running — unreachable, unstoppable, still writing to its sink. Spark rejects a duplicate *active* name; a new `_register` helper now enforces it (a stopped name is free to reuse). Applied to both the single-node and distributed launchers. |
| S3 | robustness | `start_streaming_query` registered the query in `_ACTIVE` *before* `engine.start()`, which opens the sink and recovers from the checkpoint. If either raised, the never-running query lingered in the registry as a phantom active stream. `start()` is now wrapped so a failure deregisters it. Applied to both launchers via the shared `_deregister` helper. |
| S106 | bug | **The distributed launcher's worker-count probe silently consumed a discovery pass.** `_drain_workers` sizes the fan-out with `len(source.splits())`, and the rest of the engine treats `splits()` as a question — but the incremental file source answers it by *claiming* the files it returns: they become pending and are withheld from every later pass until the epoch that read them is published. The probe therefore took a whole pass of new files that no epoch ever read, and on a continuous stream they stayed stranded for the life of the run. A claiming source is now recognized by the `confirm` half of that protocol (the same marker `LocalRunner` uses) and sized from the CPU count instead (`api/streaming/_distributed.py`). |
| S107 | robustness | `start_distributed_stream` left its `CheckpointStore` open when `engine.start()` raised — two SQLite connections per failed start, plus their WAL sidecars. The single-node launcher had already been given this cleanup; the distributed one had not (`api/streaming/_distributed.py`). |
| S102 | bug | **A drained source's final position was never checkpointed, so every restart replayed its last window — as duplicate output.** The engine write-aheads the position after each `stage()`, which is wrong for any source whose cursor advances at the *end* of a read rather than per batch. The Delta change feed is the clear case: it reads every commit since the last pass as one window, streams it batch by batch, and advances its version only once the window is fully handed over — deliberately, so a consumer that dies mid-drain replays rather than skips. Every batch of that window therefore recorded the *pre-window* version, and recovery resumed at the last committed batch id with that stale version and re-read the whole window under **new** batch ids, which the sink's by-batch-id idempotency could not absorb. The rows were written twice, silently, once per restart (pinned by `test_delta_stream_checkpoint_resumes_by_version`, which failed at `HEAD`). The moment a source reports itself spent is the first moment its terminal position is both true and stable, so `_checkpoint_drain` records and commits it there under a row-less marker batch (`core/streaming_query.py`). |
| S103 | bug | The marker batches added by S69 and S102 committed a *position* without a *state snapshot*, and recovery restores the snapshot belonging to the last committed batch — so a committed batch with no snapshot beside it silently resumed a stateful query with **empty** state. A drain marker that carried only the position fixed the position and broke the fold: a resumed `group_by(...).count()` restarted from zero and its final counts covered only the second run's rows. Both markers now go through `_commit_microbatch`, which snapshots, commits, and prunes together (`core/streaming_query.py`). |
| S89 | robustness | Nothing ever closed the `CheckpointStore`. It holds two SQLite connections for the life of a query, so a driver that starts and stops queries — a scheduler, a notebook, a test suite — leaked two file descriptors per query until the objects happened to be collected, and under WAL (S66) left the `-wal`/`-shm` sidecars behind with them. The store's lifetime is exactly the micro-batch loop's, so the loop's `finally` closes it; the launcher closes it too on the path where `start()` raises before the loop exists (`core/streaming_query.py`, `api/streaming/_launch.py`). |
| S90 | robustness | `stop()` joins the loop thread with no timeout, which is right — returning while the loop still writes to the sink would be worse — but it was also *silent*. A stop is observed only between micro-batches, so a source inside a blocking read holds the join for as long as that read takes and the caller cannot tell a slow drain from a permanent hang. The join now emits a periodic warning naming the condition and what to check, the way Carbonite's distributed barrier does (`core/streaming_query.py`). |
| S11 | feature | `StreamingQueryEngine.status()` reported `message="Stopped"` for a query that *failed*, indistinguishable from a clean stop unless the caller used `await_termination`. It now surfaces `"Failed: <type>: <msg>"` so a caller polling `status` sees the failure and its cause (`core/streaming_query.py`). |
| S18 | feature | Added `StreamingQueryProgress.output_rows_per_second` — emission throughput, distinct from `input_rows_per_second` (arrival throughput): a filter or windowed aggregate emits far fewer rows than it reads, so the two diverge and both are worth exposing (`plan/streaming/spec.py`). |
| S121 | feature | **A streaming query could not say whether it was keeping up.** `StreamingQueryProgress` reported duration and throughput, which answer how *fast* a micro-batch ran and cannot answer whether that was fast *enough* — "enough" is the trigger interval, and the record did not carry it. So a query falling further behind its source every batch looked healthy right up until someone checked the lag by hand, which is the opposite of what a low-latency stream needs from its own metrics. Added `behind_by_ms` (milliseconds the batch overran its cadence) and the `is_behind` predicate, measured by the engine against the trigger it fires on, `0` for a trigger with no interval. `__str__` names the overrun, so `recent_progress()` reads honestly (`plan/streaming/spec.py`, `core/streaming_query/engine.py`, `docs/user-guide/streaming.md`). |

## Streaming sources and sinks (`io/formats/streaming`)

| # | Cat | Improvement |
|---|-----|-------------|
| S4 | perf | `SeenStore.confirm()` (the Auto Loader durable dedup) committed once per file — one fsync each. Added `SeenStore.mark_many`, a single `executemany` + one commit, so confirming a discovery pass of N files costs one fsync (and one atomic transaction) instead of N (`seen_store.py`, `autoloader.py`). |
| S5 | bug | The Event Hubs source read each payload with `body_as_str()` then re-encoded to UTF-8 — a binary payload (protobuf/Avro/compressed) raised `UnicodeDecodeError`, and a non-UTF-8-but-decodable one was silently mangled. Now reads raw bytes via `body_as_bytes()` through the new pure `_event_to_message` helper (`eventhubs.py`). |
| S6 | bug | The Event Hubs `partition_key` (a `str`) was passed into the `key` column declared `pa.binary()`, raising `ArrowTypeError` in `_make_batch`. Now coerced to `bytes` (and `None` preserved) by `_as_bytes` (`eventhubs.py`). |
| S7 | robustness | The Event Hubs `_poll` created a per-partition AMQP consumer (`_create_consumer`) on every poll and never closed it — a continuous stream leaked one consumer (socket + threads) per partition per poll. Each consumer is now closed in a `finally` (`eventhubs.py`). |
| S26 | bug | The Event Hubs source ignored checkpointed positions on recovery: it always rebuilt each consumer at the configured `starting_position`, silently replaying or skipping on every restart, while `kafka`/`kinesis`/`pulsar` all honor their checkpoint. Now each message carries its offset string as `resume_token`, and `_poll` resumes each partition from `_resume_from` (populated by `seek`) — real exactly-once recovery (`eventhubs.py`). |
| S104 | feature | The Delta change-feed source read *every* commit since the last pass as one micro-batch window. The rows already stream batch by batch so memory is bounded, but the **epoch** is not: the micro-batch does not end until the whole backlog drains, so the trigger cadence collapses and nothing is checkpointed until it finishes — worst on a first run (the table's entire history) and on a resume after downtime, which are exactly the cases where it hurts. Added `max_versions_per_trigger`, the change-feed analogue of Auto Loader's `max_files_per_trigger` (S15), draining a backlog across many bounded epochs (`lakehouse/delta/stream.py`). |
| S105 | perf | Every streaming pass built **two** `DeltaTable` handles — one to read the latest version, one to open the change feed — and constructing one parses the transaction log. On a table with a long history that is the dominant per-trigger cost and it grows with the table. The handle is now built once and refreshed with `update_incremental`, which reads only the commits added since, with a rebuild fallback for an older delta-rs (`lakehouse/delta/stream.py`). |
| S93 | bug | The Pub/Sub `_poll` asked for `poll_size` messages, but the API caps a synchronous `pull` at 1,000 and rejects a larger request with `InvalidArgument` — so the engine's own 16,384-row default was never a legal request. Clamped to the ceiling, the way the Kinesis `GetRecords` limit already is (`pubsub.py`). |
| S94 | bug | `_commit_delivered` sent a whole poll's ack ids in one `acknowledge`. The API bounds a request at 512 KiB and an ack id runs to a couple of hundred bytes, so a full poll's worth overflowed it — and it failed the **commit**, not the read: the epoch was published and then every message in it came back on the next poll. Now chunked (`pubsub.py`). |
| S95 | perf | **Event Hubs opened a fresh AMQP consumer per partition on every poll.** S7 fixed the leak by closing each in a `finally`, at the cost of a full link negotiation and teardown per partition per poll — eighty a second on a 100ms trigger over an eight-partition hub, before a single event is read — and it discarded the consumer's own prefetch, so every poll started with an empty local buffer. Consumers are now opened once and reused; `_apply_seek` drops the one being repositioned so recovery still rebuilds at the checkpointed offset, and `close()` releases them all (`eventhubs.py`). |
| S96 | perf | The Event Hubs poll waited `max_wait_time` on *each* partition, serially, so the effective trigger cadence was `partitions x wait` — eight seconds of latency per poll on an idle eight-partition hub. Only the first partition now waits; the rest drain what has already arrived (`eventhubs.py`). |
| S97 | perf | `EventHubsSource._poll` called `get_partition_ids()` — a management round-trip to the service — on **every poll**, for a value that changes only when the hub is rescaled. Fetched once (`eventhubs.py`). |
| S98 | robustness | `EventHubsSource.close()` reset `_client_obj` only after the client's own `close()` returned, so a failing close left the handle set and the second `close()` — which `iter_batches` guarantees from its `finally` — re-closed a dead client and raised again over the original error. Same fix as S46/S57 (`eventhubs.py`). |
| S8 | bug | The `socket` dev source stripped only `\n`, so a CRLF (`\r\n`) producer left a trailing `\r` in every `value`. Now `rstrip("\r\n")`; also removed the always-empty `buf` dead variable (`dev.py`). |
| S9 | bug | The Kinesis source reused a closed shard's stale iterator forever: a `GetRecords` with no `NextShardIterator` (a drained/closed shard) left the old iterator in `_iterators`, so the next poll raised `ExpiredIteratorException` in a loop. The shard is now retired into a `_closed` set and dropped from `_active_shards` (`kinesis.py`). |
| S25 | robustness | A Kinesis `ProvisionedThroughputExceededException` (the 5-TPS/shard `GetRecords` cap — routine back-pressure) crashed the whole query. Now a throttled shard is skipped for that poll (its iterator unchanged, records read next poll) with no blocking sleep, so the trigger cadence paces the retry. `_is_throttle` matches both the exception class name and the boto `ClientError` code (`kinesis.py`). |
| S13 | feature | The Kafka poll timeout was hard-coded at `1.0s`, coupling both stop-latency (a `stop()` is only observed between polls) and poll efficiency to a constant. Added a `poll_timeout` option (kept out of the confluent-kafka config so it can't leak as a bogus `poll.timeout` key) (`kafka.py`). |
| S14 | robustness | A Pub/Sub `pull` with no deadline blocks indefinitely on an idle subscription, stalling the trigger cadence and `stop()`. Added a bounded `pull_timeout`; a deadline hit with no data (`DeadlineExceeded`/`RetryError`, matched by name so `google-api-core` need not import) is treated as an empty poll, while a real error still propagates (`pubsub.py`). |
| S15 | feature | The incremental file source (Auto Loader analog) ingested an entire backlog in one micro-batch. Added `max_files_per_trigger` (Spark `maxFilesPerTrigger`) backpressure: a pass admits at most N new files, oldest-name-first, leaving the rest undiscovered for later passes so a large backlog drains across bounded epochs (`autoloader.py`). |
| S17 | feature | The Pulsar `receive` timeout was hard-coded at 1000ms, coupling stop-latency and idle-poll latency to a constant (same class as S13). Added a `receive_timeout_millis` option, kept out of the client options (`pulsar.py`). |
| S20 | perf | `RateSource._make_batch` built each batch's timestamps with a Python list comprehension over `n` `datetime` objects — O(rows) Python in the data plane, the exact hot-path tuple touch the architecture rule forbids. Vectorized to `np.arange` + a single `pc.multiply(...).cast(timestamp[us])`, proven bit-identical to the old closed form across `rps ∈ {1,2,7,1000}` (`dev.py`). |
| S85 | robustness | `RateSource` accepted any `rows_per_second`, but the `timestamp` column is `timestamp[us]`: above one row per microsecond the spacing `1_000_000 // rps` floors to **zero** and every row gets the epoch. That is not a slow stream but a silently wrong one — a windowed aggregate puts the whole run in one bucket and the watermark never advances. Now refused at construction with a message naming the resolution limit (`dev.py`). |
| S86 | robustness | A paced `RateSource` sleeps a full second between batches, so stopping a query reading one waited out that sleep before the driver thread could be joined. It now accepts the same `set_stop_signal` predicate the brokers take (S70) and checks it before each batch and in short slices *during* the nap, so a stop is observed in milliseconds instead of at the next tick (`dev.py`). |
| S87 | bug | The `socket` dev source stamped `datetime.now()` — **local** wall clock — into a zone-less `timestamp[us]` column that every other streaming source fills with UTC. A socket stream joined or watermarked against a Kafka stream therefore sat a whole UTC offset away, which reads as "no matches" rather than as a timezone mistake. Now UTC (`dev.py`). |
| S88 | perf | `SocketSource._batch` built the timestamp column as `[now] * len(lines)` — a Python object per row in the data plane, the same shape S20 vectorized out of `RateSource`. Now a single numpy broadcast of the scalar (`dev.py`). |
| S38 | robustness | The base broker `_poll_loop` re-polled immediately on an empty poll (`if not messages: continue`), spinning a full core for any broker whose `_poll` returns at once when idle — Kinesis `GetRecords` always returns, and a shard skipped for throttling (S25) returns empty instantly, so the loop hammered the rate-limited API into more throttling. Added a geometric back-off between empty polls, capped at 250ms and reset on real data, so an idle fast-empty broker rests instead of spinning; a broker whose `_poll` already blocks (Kafka) rarely reaches it (`broker.py`). |
| S39 | robustness | `DeltaStreamSink.write_batch` guarded exactly-once with only a non-atomic `is_committed` pre-check, so two writers sharing an `app_id` (concurrent drivers, or a query racing its restart) both passed the check and the loser's commit crashed the query with a `CommitError` even though the batch was durably committed by the peer. The commit is now wrapped: on `CommitError` it re-reads the log and treats a now-recorded transaction as benign, re-raising only when the transaction is genuinely absent (`sinks.py`). |
| S40 | robustness | `ForeachBatchStreamSink`/`ForeachStreamSink` returned `None` tokens, unlike the File/Delta sinks whose batch-id-bearing tokens the commit-log `sink_token` column records. They now return `foreach_batch:{batch_id}`/`foreach:{batch_id}`, honoring the `StreamSink` token contract uniformly so the commit-log can dedup a replayed `foreachBatch` once the runner is wired to pass the token through (`sinks.py`). |
| S41 | perf | **Kafka poll latency was pinned to `poll_timeout`, not to when data arrived.** `Consumer.consume(num_messages=N, timeout=T)` does not return as soon as records are available: librdkafka keeps popping against the *remaining* timeout until it has N, so a topic producing a few records per trigger answered a 16,384-message request only when the full second expired. Every micro-batch cost a fixed second no matter how promptly the record landed, and raising `poll_size` for throughput made it worse. `_consume_eagerly` now blocks for **one** record, then drains the already-fetched queue with `timeout=0` up to `poll_size`: latency becomes time-to-first-record, throughput is unchanged (`kafka.py`). |
| S42 | bug | The Kafka `_poll` dropped every errored record (`if rec.error() is None`) — right for a partition-EOF marker, catastrophic for anything else. An unknown topic, a failed SASL handshake, or an out-of-range offset arrives as an errored record on *every* poll, so the source returned an empty list forever: the query stayed "running", read nothing, reported no failure, and the empty-poll back-off made it look idle rather than broken. `_is_benign_record_error` now skips only partition-EOF and librdkafka-retriable codes; anything else raises a `BackendError` naming the topic (`kafka.py`). |
| S43 | perf | The distributed epoch read built a **fresh broker client per micro-batch**. A 200ms trigger tore down and rebuilt a Kafka consumer five times a second per partition — TCP connect, metadata fetch, group join, seek — all serialized ahead of the poll that reads data, and a client that lives one poll can never prefetch, so each epoch paid a full round-trip for its first record. `BrokerSplit._epoch_reader` keeps consumers warm per worker process (LRU-capped, closed at exit). Reuse is conditional on *contiguous* resumption: any other requested position closes the consumer and seeks a fresh one, so the cache can cost a reconnection, never a wrong row (`broker.py`). |
| S44 | bug | `BrokerSplit.read_epoch` returned `None` as the new position when a poll carried nothing for its partition. `_read_epoch` drops a `None` position from the epoch's offset map, so that does not mean "unchanged" — the driver *loses* the partition's checkpoint and the next restart replays from `auto.offset.reset`. Now falls back to the offset the epoch started from (`broker.py`). |
| S45 | robustness | `KafkaSource._discover_partitions` called `list_topics` with no timeout and indexed `meta.topics[topic]` directly. Wrong or unreachable bootstrap servers blocked the *driver* forever while planning a distributed read, presenting a configuration typo as a hung `collect()`; a missing topic raised a bare `KeyError` on the topic name. Now bounded by a `metadata_timeout` option (kept out of the client config) and reports a missing topic and a topic-level metadata error as actionable `BackendError`s (`kafka.py`). |
| S46 | robustness | `KafkaSource.close()` left `_consumer` set when the client's own `close()` raised (a broker already gone, a group-coordinator leave that timed out). `iter_batches` guarantees a second `close()` from its `finally`, which then re-closed a dead consumer and raised again — out of a `finally`, masking the original error. The handle is now dropped before the failing call (`kafka.py`). |
| S47 | robustness | `_commit_delivered` let librdkafka's `_NO_OFFSET` kill the query. It means "this consumer holds no stored position for its assignment", which happens whenever a rebalance revoked the partitions between the poll and the publish — a condition the next poll resolves, and one Batcher's own offset log already covers since `_on_assign` resumes from it, not from the group offset. Now treated as benign; every other commit failure still propagates (`kafka.py`). |
| S48 | perf | The empty-poll back-off (S38) was charged to brokers that had *already* blocked. Kafka waits up to `poll_timeout` for its first record, then slept up to another 250ms on top — pure added latency for the first record after an idle stretch, on the path this engine exists to be fast on. The nap is now discounted by how long `_poll` itself took, so a blocking broker pays nothing and a fast-returning one still rests (`broker.py`). |
| S49 | perf | `_make_batch` called `broker_schema()` per micro-batch, allocating six `pa.Field` objects on the latency-critical path; two batches built from separately-constructed (equal) schemas also do not share a schema pointer, so downstream concatenation fell back to field-by-field comparison. `pa.Schema` is immutable, so the schema is now built once and shared (`broker.py`). |
| S50 | robustness | The broker credential-redaction hints were simultaneously too broad and too narrow. A bare `"sas"` matched every `sasl.*` key — including the non-secret `sasl.mechanism` and `sasl.username` — so two clusters differing only in SASL identity fingerprinted identically and shared one learned-statistics entry; meanwhile an inline PEM private key (librdkafka's `ssl.key.pem`) matched no hint at all and reached both the `repr` and the persisted stats key. Hints narrowed to `sas_key`/`shared_access` and widened to cover `key.pem`, `keystore`, and `truststore` (`broker.py`). |
| S51 | bug | **A Kinesis reshard silently stopped the reader.** A shard closes only because a split or merge replaced it with children, and S9 retires the drained parent — but the shard list is cached for the whole run, so the children were never discovered. The reader went permanently quiet on that key range: every poll returned nothing, the empty-poll back-off made it look like an idle stream, and no error was raised while records piled up in shards nobody was reading. Retiring a shard now invalidates the cache, costing one `list_shards` per reshard (`kinesis.py`). |
| S52 | robustness | A Kinesis shard iterator is valid for five minutes. Any trigger interval longer than that — and any shard that goes quiet while the query polls its siblings — outlives its iterator, and the next `GetRecords` raised `ExpiredIteratorException` straight through the query. Now recognized (by class name *and* `ClientError` code, so `botocore` need not import) and healed by dropping the iterator; `_iterator` rebuilds it with `AFTER_SEQUENCE_NUMBER` from the **live** delivered sequence rather than the recovery position, so the refresh replays nothing (`kinesis.py`). |
| S53 | perf | Kinesis polled its shards in a serialized loop, so a micro-batch on a 64-shard stream cost 64 sequential HTTPS round-trips before one row reached the plan — latency scaling with the shard count, which is backwards: shards are the unit of parallelism and Kinesis rate-limits each independently. `GetRecords` now fans out across a bounded thread pool (a botocore client is thread-safe) with results merged positionally on the calling thread, so `_iterators` is still mutated single-threaded. A single-shard reader never builds a pool (`kinesis.py`). |
| S54 | perf | Pulsar charged **every** `receive` the full `receive_timeout_millis`, including the one that finds the queue empty and ends the drain — which happens on every poll. A topic delivering ten messages per trigger therefore paid a fixed second of latency just to be told it had run out. Only the first receive now waits; the rest drain at 1ms (not 0, which the client reads as "block forever") (`pulsar.py`). |
| S55 | bug | `_message_id_to_offset` packed a Pulsar entry id into 20 bits. A BookKeeper ledger routinely holds more than 1,048,576 entries, and past that the id wrapped: two different messages in one ledger folded to the same int64 `offset`, silently breaking the ordering and de-duplication that column exists for. Widened to 32 bits, which still leaves 31 for the ledger id inside int64 (`pulsar.py`). |
| S56 | bug | A Pulsar seek repositions the whole **consumer**, but the base `seek` walks a checkpoint partition by partition — so a multi-partition checkpoint issued one seek per entry and the last silently won, resuming every other partition at a position belonging to a different one. `PulsarSource.seek` now refuses an ambiguous multi-partition resume with a `PlanError` naming the fix (one split per partition), instead of quietly replaying or skipping. `_apply_seek` also drops the polled-but-unpublished handles, which the new position is about to redeliver (`pulsar.py`). |
| S57 | robustness | `PulsarSource.close()` closed the consumer before the client and reset neither attribute until after its call succeeded. A consumer `close()` that raised therefore skipped the *client* close entirely — stranding its IO threads — and left both handles set, so the `close()` that `iter_batches` guarantees from its `finally` re-closed dead handles and raised again over the original error. Both handles are now dropped first and the client is released in a `finally` (`pulsar.py`). |
| S58 | perf | `PulsarSource._client()` called `_import_pulsar()` on entry, before checking whether anything needed building — re-entering the import machinery on every poll and every commit for a module the already-built consumer proves is present. Moved into the construction branch (`pulsar.py`). |
| S59 | robustness | Once a broker consumer outlives the epoch (S43), a client that holds delivered-but-unreleased messages grows without bound — Pulsar keeps every un-acked handle so `_commit_delivered` can ack them, and the distributed path never called it. `_epoch_reader` now releases the previous epoch when the driver asks to resume from exactly where that epoch stopped, which is the one point on that path where it is provably behind us; recovery there is driven by the driver's write-ahead log via `seek`, never by the broker's own cursor (`broker.py`). |
| S60 | perf | The Auto Loader seen-store ran in SQLite's default rollback-journal mode, which rewrites and fsyncs a journal file around every commit — and this store commits once per discovery pass, so a 200ms trigger paid two full journal cycles a second to remember a handful of filenames. Now opened in WAL with `synchronous=NORMAL`, which is not merely faster but the *correct* durability point here: under WAL it still survives a process crash, and what it gives up (the last commits after an OS crash) re-offers those files, which the epoch's transaction already makes idempotent. The store must never remember a file whose rows were not published, and NORMAL cannot produce that. Both pragmas are best-effort, so a mount that refuses WAL still works (`seen_store.py`). |
| S61 | perf | `IncrementalFileSource` opened a fresh SQLite connection — preceded by a `mkdirs` — inside **both** `discover()` and `confirm()`. A streaming query calls both once per trigger and the distributed driver's idle poll re-lists on top of that, so a 200ms cadence spent four filesystem round-trips a second before listing a single file. The store is opened once for the life of the source, with an idempotent `close()` (`autoloader.py`). |
| S62 | perf | `IncrementalFileSource.complete()` deduped with `f not in self._completed` — a linear scan of the completion list per file. Draining a backlog (which is exactly what `max_files_per_trigger` exists to make possible) is therefore quadratic in the backlog: 100k files cost 5 billion comparisons in the control plane. A parallel membership set makes it linear (`autoloader.py`). |
| S63 | robustness | `IncrementalFileSource.schema()` handled only the `expand`-raises spelling of "the directory is empty". A filesystem that returns an empty list instead reached `files[0]` and surfaced a bare `IndexError` naming neither the path nor the suffix. Both spellings now produce the same actionable `IOError` (`autoloader.py`). |
| S64 | perf | `MemoryStreamSink` re-summed `nbytes` across **every** retained table on every micro-batch to check its cap — so the guard against unbounded growth was itself quadratic in the number of micro-batches, getting slower exactly as the thing it watches got bigger. Replaced with a running total, reset by `open()` (`sinks.py`). |
